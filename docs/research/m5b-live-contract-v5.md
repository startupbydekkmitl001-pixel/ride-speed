# M5B friend links and foreground convoy contract

Implementation contract frozen by root on1October2026, including the approved exact unknown-grant cancellation fence. Root separately authorized additive008 and local tests; this document does not authorize hosted deployment or live-location activation. Preserve deployed001–007 and their existing capture, Auth, receipt, RLS, safe-route and binary-first deletion behavior. This narrows the earlier [M5 audit](m5-friends-challenges-v5.md) into the next implementable slice after [M5A](m5a-social-contract-v5.md).

The user's full M5 remains required: QR/invite links, foreground four-person convoy now; approved async route-time, live race timing, multi-recipient challenges and push delivery follow in separate slices. A convoy is a normal group trip with metric `none`; it creates no verification, race result or leaderboard eligibility.

## 1. Chosen boundaries

Use typed authenticated Postgres RPCs for control, a latest-position row for each participant, and private Realtime **invalidation only**. Each position read checks current membership, host friendship generation, every room block, sender ghost/consent/TTL and both accounts again. This permits revocation even when an old socket remains subscribed. Client-to-client GPS Broadcast would have lower read traffic but cached channel authorization and replay retention make its revocation/retention contract harder; a new custom streaming server adds credentials and operational scope. The latest-row approach is the first free pilot.

Initial caps are **four accepted participants including the host, two unexpired rooms in the project, one nonterminal membership per account, at most1Hz publication and position read**. A requested join does not grant room-peer visibility or location access. Members must be accepted friends of the host; they need not be friends with each other, but no blocked pair may coexist. A host approves each request. Host exit/deletion and any friendship-generation change or block involving room members cancel the room; there is no automatic host transfer. A normal nonhost leave removes only that member and rotates the room topic.

Separate sending from viewing. Sending is initially `none`; exact room-scoped **precise** disclosure is explicit, expires and never restarts automatically. Viewing consenting members is an independent local toggle, initially off, and does not start GPS or require the viewer to send a position. Ghost users may view after explicitly enabling the receive toggle; ghost users cannot grant/publish their own location. This slice adds no general friends-location directory or coarse-sharing scope.

## 4. Tokens, QR and join-code admission

Issuer creates32cryptographically random bytes and canonical base64url token43characters; QR encodes `ridespeed://friend/v1/<link_uuid>#token=<token>` (`ridespeed-dev` in development). Creation sends SHA256(domain-prefix+token) only. Persist issuer token in an owner-scoped SecureStore slot **before** its create operation; ordinary account JSON contains only link ID/secure-slot ID/hash. Lost create response retries the exact UUID/hash. New devices cannot recover old QR plaintext from the server: create a new link. Do not put a token in query strings, analytics, logs or crash breadcrumbs. Link grants a minimal preview and a request; it never accepts friendship or grants location. An HTTPS universal-link landing page/domain and installation fallback are a later explicit setup gate; installed-app scheme/QR flow works first.

The foreground scanner requires the SDK-compatible camera module and localized camera purpose string; render QR from deterministic encoded bytes with an audited encoder. Manual link/code entry remains available if permission is denied. Deep-link parsing validates scheme/version/UUID/fragment alphabet/length, stores an incoming intent in memory or a short-lived SecureStore slot across login, and presents the identity preview after current Auth scope is established. It performs no automatic resolver/mutation on app launch and never carries a former owner's token through A→B→A without fresh user action.

Room host generates eight Crockford Base32 characters (`0–9,A–Z` excluding`I,L,O,U`,40bits), persists the raw code in owner SecureStore, and sends only its domain-separated SHA256. Normalize user entry by removing display hyphens/spaces and uppercasing, then validate exactly eight characters. `rs_resolve_convoy_code` receives plaintext in a POST body, consumes committed admission, requires current accepted host friendship and returns a short proof. A code grants request admission only; host approval plus each member's precise-location disclosure remain separate. All unavailable/expired/revoked/blocked/nonexistent resolve outcomes return the same null preview, not a directory oracle.

## 5. Exact control wire and recovery

Hash interoperability is frozen: lowercase hexadecimal SHA256 over UTF-8 `ride-speed:friend-link:v1:` followed by the canonical43-character base64url token, or `ride-speed:convoy-code:v1:` followed by the normalized8-character uppercase Crockford code. Host code secrets are versioned by owner/resource/hash, retaining current and pending replacement until canonical `self_code.hash` selects the current code. Never overwrite the old secret before replacement acknowledgement; an old receipt replay cannot select an obsolete code after another device rotates it. Only a nonterminal host snapshot returns self_code; all other views return null.

Stored owner operations are exactly `{operationId,request,queuedAt,lastError}`. Review state is memory-only in the coordinator's reviewed/unattempted sets; suspend clears those sets and retains immutable pending rows. Restored grant/join/link-request operations are status-first, then explicitly reviewed for an exact-ID retry when no receipt exists. A persisted flag never authorizes sending or sharing.

New RPC family is separate from the frozen007 SocialRequest union. All request fields below are required, including explicit nullable fields. No arbitrary owner ID, geometry, GPS, Storage path or install token is accepted. Request JSON≤16KiB; local owner outbox≤32operations/128KiB. Additive account parser must preserve007's existing social outbox unchanged.

## 7. Rotation, lock protocol and predecessor integration

Use a single pilot-wide `ride_private.live_control_lock()` advisory xact lock (`ride-live-control-v1`). Actor calls acquire their existing **own account fence first**, then this lock **before any profile/account-state/pair/room/member/consent/position/counter row lock**. Under it, acquire needed canonical pair locks in sorted pair order, then room IDs in UUID order, then membership/consent/position rows, then admission counters. Never acquire another user's account fence under live_control. Janitor has no actor and acquires only live_control first, never account fences. This deliberately serializes the≤8publishers pilot; keep critical sections short and do no HTTP/GPS/network wait inside transactions.

Migration008 wraps these exact existing entries before their original body takes lower locks: `rs_social_mutate(UUID,JSONB)`, trusted legacy `rs_request_friend(TEXT)`, `rs_friend_action(UUID,TEXT)`, `rs_set_presence(BOOLEAN)`, `rs_heartbeat()`, `rs_update_account_state(INTEGER,TEXT,TEXT,JSONB)`, service-only `rs_begin_account_deletion(UUID,UUID)` and `rs_purge_account_data(UUID,UUID,UUID)`. Source name is `rs_update_account_state`, not an invented `rs_update_preferences`. Move each unchanged predecessor implementation to a named revoked private helper (`*_pre_live_v1`) and recreate the same public signature/security-definer/empty-search-path/current-grants entry. The entry acquires the actor/owner account fence then live_control before invoking its predecessor; social_mutate retains its existing typed auth/deletion envelope instead of changing those into thrown errors. Private predecessor helpers have no public/anon/authenticated/service_role direct EXECUTE; definers call them internally. Capture before/after relationship/ghost state and invalidate affected rooms in the same transaction. An old receipt replay causes no privacy/room mutation, and wrapper failure rolls back both the old transition/receipt and live hook. Prove internal calls still route through public wrappers and all original signatures/grants remain correct. Preserve001–007 source files and old helper/receipt semantics. No authenticated path may bypass the wrapper, including account preference writes calling presence internally; no direct privileges are restored on the six retired007 browser mutations. The unchanged heartbeat body is fenced because it locks profile/friend rows; it never implicitly renews a convoy host lease or grants location.

**Why entry wrappers are necessary:** taking live_control only inside `pair_lock` is too late:007 handle request already holds a target profile share lock, and002 preference update already holds an account-state row lock. A concurrent control holder seeking those rows would invert the order. Likewise deletion quarantine cannot set an inactive account or rotate friendships first and join room locking afterwards. Wrap the original entry before those locks. Profile-only/avatar/garage/route writers never acquire live_control later; audit them for accidental new calls. Room projection creation uses current route read/share locking under live_control; route writers do not call room helpers, preventing a cycle. Existing closed-course verifier grants/leases remain unchanged; M5B metric none adds no approved-course dependency.

Any accepted membership/consent/ghost change rotates topic_id and increments topic_generation/change_revision in the **same transaction**, clears all room positions, and revokes only affected sender leases. Other members' still-valid original consent expiry remains intact; their sampler must read the new epoch before publishing again. Block or host-friend generation change among any requested/accepted member cancels the room, invalidates code/proofs, clears all positions and all grants. Unblock/re-friend never revives it. Voluntary nonhost leave removes only that member; host background/lease expiry/end/leave/deletion ends or cancels the room, releases its slot and revokes everyone.

Before rotation emit one GPS-free `room_changed` hint on the retired topic with its **old** generation; current honest clients use it to refetch. Thereafter no publish/control path emits future events on that retired topic. Cached removed sockets may receive this final opaque hint but no location or future activity stream.
