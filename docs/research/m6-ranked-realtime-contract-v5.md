# M6 bounded board invalidation — proposal, not deployed

The current010 board uses finite canonical refresh. It has no table subscription or live-board claim. A later additive migration can introduce one private authenticated pilot topic with the exact nongeographic hint `{schema_version:1,type:'ranked_invalidate'}`. Never include owner/result/course IDs, filter, score, count, revision, timestamp, location or Storage paths. Canonical Ranked RPC reads remain the only data authority.

Keep at most one subscribed Ranked topic per installed owner generation, only while the Ranked screen is focused/foreground and permitted by the parent. Debounce/coalesce hints, honor the shared60/minute read budget and retry-after, remove the channel on blur/background/account change, and perform a guarded first-page read after reconnect. A retained socket's cached permission cannot authorize board rows or restore a revoked audience. A hint only means the client may reread.

Server design must coalesce to at most one hint per10s globally while enabled, without per-recipient inserts or copying board payloads. Candidate dirty state has one bounded private row and one service janitor emission; exact operator scheduling and hook inventory need review before code. Audit qualified result finalizers, publication, course approval/discovery revocation, moderation, friend/block changes and account deletion. Every hook must enter existing own-account→global ordering before lower rows, preserve worker leases and never acquire a foreign account fence. Deletion and blocked viewers still reauthorize each RPC. Disable the hint independently of result qualification.

Emission caps are not message-budget guarantees: fanout and reconnects count too. Measure actual active channels and organization usage; choose a small pilot subscriber cap and stop emitting before shared headroom is exhausted. Never add a global feed of private table changes. A later slice should test committed coalescing, mutation rollback, account transition/blocked socket behavior, error/backoff/reconnect, retained callback guards and actual managed private sockets before describing boards as realtime.

Primary documentation checked2026-10-01: [Supabase Broadcast](https://supabase.com/docs/guides/realtime/broadcast) supports database-origin private hints; [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization) describes channel policy behavior; [Realtime limits](https://supabase.com/docs/guides/realtime/limits) and [billing](https://supabase.com/docs/guides/platform/billing-on-supabase) define shared project/organization limits. This is an architectural proposal; local tests do not certify managed socket delivery, free-tier fanout or physical UI latency.
